# Driver and Dispatcher Support Handover Implementation Plan

> **For agentic workers:** Execute this plan in order, checking each step. Read `rules/rules_backend.md`, `rules/ui_rules.md`, and `lib/core/errors/` before implementation. Do not dispatch subagents unless the user explicitly requests delegation.

**Goal:** Integrate the driver issue and reassignment flow, dispatcher decisions and custody handover, and the three replacement driver screens from Figma without changing the app's existing visual language.

**Architecture:** Extend the existing feature based Clean Architecture: UI → Event → ViewModel → UseCase → Repository → Remote Data Source → `ApiServices`. DTOs stay in data, entities in domain, and errors flow through `safeApiCall`, `Failure`, and Core error widgets. Keep the existing dispatcher support, driver delivery issues, and driver pickup features; add a separate driver support handover feature because kitchen pickup and driver to driver handover are different operations.

**Tech Stack:** Flutter/Dart, Dio/Retrofit, json_serializable, GetIt manual registration in `lib/core/di/di.dart`, flutter_bloc, mobile_scanner, google_maps_flutter, geolocator, SignalR client infrastructure.

## Global constraints and backend contract

- Preserve unrelated local edits. At plan time `lib/core/network/network_constants.dart` is modified and `docs/superpowers/plans/2026-10-20-native-driver-voice-calls.md` is untracked. Check `git status` before each edit; never reset these changes.
- The backend addition requires migration `AddDriverReassignmentDecisions`. Before live API testing, confirm it is deployed to the target environment. A Git commit is not proof of deployment.
- Use existing `ApiServices`, injected Dio, token/language interceptors, `ApiResult`, `safeApiCall`, `lib/core/errors/`, `lib/core/di/di.dart`, and the existing event/state/ViewModel style. Do not create another client or result/error abstraction. Do not hand edit generated Retrofit or JSON files; regenerate them.
- UI follows `rules/ui_rules.md`: `context.colorScheme`, `context.localization`, theme styles/spacing, directional layout, one custom widget per file, no hardcoded user text/colors, reuse existing map/scanner widgets where feasible, no new package without user direction.
- API paths below have `/api/v1` prefix. `boxId`/`tripStopId` is `TripStop.Id` UUID. `replacementDriverId` is `DriverProfile.Id`. `issueId`/`requestId` is the persisted complaint ID. `handoverId` identifies a custody operation. Do not substitute box display codes or account IDs.
- Success responses are unwrapped JSON. `POST report-issue` returns a JSON string UUID; `POST report-delay` returns JSON boolean `true`; `POST request-reassignment` returns its direct response object. `Utc` timestamps stay UTC in data/domain and are converted only for display.
- Backend failures are ProblemDetails with `code` and localized `detail`; some validation failures include `errors`. Match `Failure.code`/`ApiException.backendErrorCode`, never localized text. Initial load failure with no data → `ApiErrorWidget`; partial or form failure → `InlineApiErrorWidget`; successful empty data → `EmptyStateWidget`; keep prior content on refresh failure.
- Driver issue: `POST /driver/orders/{boxId}/report-issue` body `issueType` required, `description` optional after trim max 250, `severity` optional `Low|Medium|High` default `Medium`, `evidencePhotoStorageKey?`, `evidencePhotoStorageKeys?` merged unique max 3. Allowed issue types: `AddressIssue`, `SevereDelay`, `RoadIssue`, `VehicleBreakdown`, `TrafficAccident`, `SevereWeather`, `CustomerUnavailable`, `CustomerRefusal`, `DamagedBox`, `Other`. No GPS in this request. General issue requires an active assignment, not specifically `PickedUp`.
- Image upload before report: `POST /uploads` multipart parts `file`, `folder=issue-evidence`, `scope=drivers`; JPEG/PNG/WebP, file max 25 MB, response `201` with `storageKey`. Report body uses storage keys, never `readUrl`. The report rejects missing, another driver's, or invalid type keys; images are optional.
- Driver delay: `POST /driver/orders/{boxId}/report-delay`, `delayMinutes` 1..1440, optional `reason`. Backend builds `Delay reported: {minutes} minutes. Reason: {reason}` and limits the entire string to 250 characters. Requires active assignment; not for Delivered/ReturnedToKitchen. Does not transfer custody or fail the stop.
- Reassignment POST: `POST /driver/orders/{boxId}/request-reassignment`, `reason` one of `VehicleBreakdown|TrafficAccident|MedicalOrPersonalEmergency|DeviceFailure|OtherOperationalReason`, optional `notes` max 250, optional complete WGS-84 latitude/longitude pair. Requires `PickedUp`, active assignment, valid account, no active handover/open follow-up, trip not Completed/Cancelled. Response `{requestId,boxId,boxCode,status:'ReassignmentRequested',message,requestedAtUtc}`. Duplicate active request → 409 `driver.reassignment.request_already_active`.
- Driver request recovery: `GET /driver/reassignment-requests?boxId={tripStopId}&page=1&pageSize=20` returns a direct array, newest first; page size max 100, `boxId` optional. `GET /driver/reassignment-requests/{requestId}` returns a single object. Fields include `status`, `reason?`, `notes?`, `decision?`, `decisionNotes?`, `decidedByUserId?`, `decidedAtUtc?`, `handoverId?`, `handoverStatus?`, `replacementDriverId?`, `replacementTripId?`, `latitude?`, `longitude?`; old records can have null box/reason/notes. Statuses: `ReassignmentRequested`, `Accepted`, `Rejected`, `Closed`. `decision` is separate from handover status. On lost POST response, GET by known box; if empty and retry yields active conflict, GET again before showing persisted success.
- Dispatcher decision: `GET /dispatcher/reassignment-requests/{requestId}`; `POST /dispatcher/reassignment-requests/{requestId}/accept` with optional `notes` max 500; `/reject` requires `notes` 3..500. Both return the updated request. Repeated same decision and cleaned notes is idempotent; changed decision/notes → 409 `REASSIGNMENT_ALREADY_DECIDED`. Reject closes complaint and prevents handover. Accept does not select a driver or transfer custody. `resolve` while decision pending → `REASSIGNMENT_DECISION_REQUIRED`. A direct assign may atomically accept for legacy compatibility, but the new UI should show the explicit decision first.
- Dispatcher support APIs already partly integrated: `GET /dispatcher/support/issues` with status/area/search/date/page filters; `GET /dispatcher/support/issues/{issueId}`; `GET /dispatcher/support/issues/{issueId}/candidates?pageNumber=1&pageSize=20`; `POST /dispatcher/support/issues/{issueId}/resolve` with `resolutionNotes` 3..500. Keep server pagination/counters and restaurant scoping. Candidate rating, distance, ETA, area, names/phones may be null; never turn absent commercial data into `0`, a made up name, or ETA.
- Preferred handover create: `POST /dispatcher/support-handovers/issues/{issueId}/assign` body `{replacementDriverId,idempotencyKey,notes?}`. Stable key max 100, persist across retry of the same issue/driver/notes operation. Response is handover object. Do not use legacy `/dispatcher/support/issues/{issueId}/reassign` for the new flow because its name/result can imply immediate transfer. Existing use of legacy route must be migrated carefully.
- Handover reads: dispatcher `GET /dispatcher/support-handovers?status=Assigned&restaurantId={id}&page=1&pageSize=20` and `GET /dispatcher/support-handovers/{handoverId}`; driver `GET /driver/support-handovers?status=active` direct array and `GET /driver/support-handovers/{handoverId}`. Dispatcher list returns `{items,totalCount,pageNumber,pageSize}`, max page size 100. Driver `active` includes unfinished operations.
- Handover statuses: `Assigned` (original holds custody), `Arrived` (replacement arrival saved), `Receiving` (at least one result saved), `Completed` (settlement saved), `Cancelled`. Arrival `POST /driver/support-handovers/{handoverId}/arrival` body `{latitude,longitude}` from replacement driver. No server proximity radius is guaranteed. Pickup position is a complete pair from complaint or actual original driver tracking; `pickupLocationSource=Complaint|DriverTracking`, `pickupLocationRecordedAtUtc`. Never use customer stop or restaurant as fallback pickup point. Missing trusted point → `PICKUP_LOCATION_UNAVAILABLE`.
- Replacement records each item via `POST /driver/support-handovers/{handoverId}/boxes/scan` body `{code,status,method,followUpNote?}` where method `Barcode|ManualCode`, status `Received|Missing|Damaged`. Use actual active barcode for Barcode or exact unique `manifestCode` for ManualCode. Missing/Damaged require a follow-up note max 500. Repeating the same result while Arrived/Receiving is safe; changing it is rejected; after Completed, read details. Do not reuse the kitchen pickup endpoint.
- Completion: `POST /driver/support-handovers/{handoverId}/complete` with no body; enabled only after arrival and `pendingCount=0`. A repeated completion returns the same saved result. Only `Received` boxes move to the replacement trip. Missing/Damaged stay on original trip as `DeliveryHold` with `followUpId`/`followUpStatus`; no partial transfer. `replacementTripId` can be null when zero boxes were received. Re-read the driver's new trip/orders after completion.
- Cancellation: `POST /driver/support-handovers/{handoverId}/cancel` or dispatcher equivalent body `{reason?}` max 500. Allowed in Assigned/Arrived only with no recorded result; any receipt, including Missing, blocks cancellation. Do not erase accepted decision.
- Follow-up: `POST /dispatcher/support-handovers/{handoverId}/boxes/{tripStopId}/follow-up/return-to-kitchen` body `{manifestCode,resolutionNote}`; note 5..500; operation Completed and box Missing/Damaged with active hold on original trip. Only use after physical kitchen return verified. Result updates stop to ReturnedToKitchen and follow-up to Resolved without changing saved receipt result. Resolve issue only when no active handover/open follow-up.
- Handover object: `handoverId,issueId,tripId,originalDriverId,replacementDriverId,restaurantId,status,pickupLatitude?,pickupLongitude?,assignedAtUtc?,arrivedAtUtc?,completedAtUtc?,replacementTripId?,receivedCount,missingCount,damagedCount,pendingCount,pickupLocationSource?,pickupLocationRecordedAtUtc?,issueTitle?,issueCategory?,issueDescription?,tripCode?,originalDriverName?,originalDriverPhone?,replacementDriverName?,replacementDriverPhone?,boxes[]`. Box: `tripStopId,manifestCode,status,receivedAtUtc?,recordedAtUtc?,followUpNote?,followUpId?,followUpStatus?`. Respect nulls and keep exact manifest codes.
- SignalR events: driver hubs `/hubs/driver-hub` or `/hubs/driver` with `support-handover-updated`, `driver-support-issue-updated`; dispatcher hubs `/hubs/dispatcher-hub` or `/hubs/dispatcher` with `driver-support-handover-updated`, `driver-issue-updated`. Handover event carries `eventId,occurredAtUtc,handoverId,tripId,replacementTripId?,restaurantId,originalDriverId,replacementDriverId,status,eventName`; issue event carries `eventId,occurredAtUtc,issueId,restaurantId,driverId?,category,eventName`. `reassignment-accepted`/`reassignment-rejected` signal decision. Treat events as invalidation hints: dedupe if needed and GET authoritative state on event/reconnect; load driver active handovers on cold start. Poll/refresh fallback for missed events.
- Figma 10.14/10.15/10.16 represent replacement pickup location, scanner/manual code, and summary. Sample ETA/distance are not guaranteed backend values. Figma's “request replacement box from restaurant” text is informational only: backend has a follow-up hold, not a driver action to order a replacement. Do not invent an endpoint or show a clickable request action.

## Acceptance criteria

The original driver can create and recover a persisted complaint/request, see explicit dispatcher decisions, and follow custody progress. The dispatcher can decide, assign a replacement using a stable key, monitor custody, settle missing/damaged items, and resolve only after all blockers clear. The replacement driver can follow the Figma location/scan/summary flow, and only confirmed Received boxes enter their new trip. All failures use the existing Core error system and all views reconcile with GET after lost responses or reconnect.
