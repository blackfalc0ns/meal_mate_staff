# خطة ربط دعم السائق بالباك — تسليم إلى Gemini

**التاريخ:** 2026-10-21

**تحديث العقد:** تعتمد هذه النسخة تعديل الباك الخاص بروابط الصور الموقعة بـ`readToken` لمدة 15 دقيقة. يحل هذا السلوك محل اشتراط Bearer لكل رابط صورة؛ روابط القراءة القديمة غير الموقعة تظل محمية.

**الهدف:** استكمال ربط قائمة بلاغات السائق وتفاصيلها والصور والتحديثات اللحظية، وإعادة استخدام إنشاء البلاغ الموجود، دون شات أو إعادة تصميم الواجهة.

**المعمارية:** Feature-Based Clean Architecture الموجودة في المشروع، باستخدام Dio وRetrofit وflutter_bloc وGetIt/Injectable وApiResult وsafeApiCall الحالية.

**نطاق هذا الملف:** خطة تنفيذ فقط. لا تعني أن التكامل أو النشر تم بالفعل.

- لا تخترع endpoint أو حقولًا أو حدود رفع غير موثقة.

التدفق الإلزامي:

```text
UI → doIntent(Event) → ViewModel → UseCase
→ Repository Contract → Repository Impl
→ Remote Data Source → ApiServices

Response DTO → Mapper → Domain Entity
→ ApiResult → State → UI
```

## 4. نماذج البيانات والـMapping

- [ ] استخدم `json_serializable`، واجعل حقول Response DTO nullable دفاعيًا، بما فيها القوائم والعناصر المتداخلة حسب أسلوب المشروع.
- [ ] اجعل Request DTO يتبع المتطلبات الحقيقية للعقد، ولا تجعل المطلوب اختياريًا بلا سبب.
- [ ] لا تمرر DTO إلى Domain أو UI، ولا تضع JSON parsing داخل ViewModel.
- [ ] استخدم كيانات منفصلة للقائمة والتفاصيل إذا كانت توسعة الكيان الحالي ستجعل حقول التفاصيل إجبارية على القائمة.
- [ ] احفظ التواريخ كقيم `DateTime` ذات معنى UTC، ونسقها للغة ومنطقة الجهاز في طبقة العرض.
- [ ] اترك بيانات الطلب والتواريخ الاختيارية nullable؛ لا تحولها إلى طلب أو تاريخ وهمي.
- [ ] اعرض `categoryLabel` و`statusLabel` كما يرجعهما الخادم.
- [ ] افصل حالة العرض `status` عن `rawStatus`.
- [ ] تعامل دفاعيًا مع القيم غير المعروفة دون تصنيفها تلقائيًا كبلاغ محلول أو اختلاق مرحلة.
- [ ] لا تعطِ بلاغًا بلا معرف معرفًا وهميًا، ولا تتيح استدعاء التفاصيل بمعرف فارغ.

المطابقة مع enum التايملاين الحالي:

```text
Current    → inProgress
Completed  → completed
Unrecorded → pending
```

`pending` هنا يعني عدم تسجيل حدوث المرحلة، وليس أنها حدثت. استخدم labels وترتيب المراحل من الخادم، ولا تستنتج توقيت المراجعة أو الاتصال من `updatedAtUtc` أو الحالة العامة.

## 6. ViewModel وState للقائمة

- [ ] استخدم sealed Events ومدخل UI عامًا واحدًا `doIntent`، مع handlers خاصة.
- [ ] استخدم State immutable مع `copyWith` حسب قواعد المشروع، مع إمكانية تصفير failure والـfeedback صراحة.
- [ ] أضف أحداث التحميل الأولي، تغيير البحث، تغيير الفلتر، تحميل الصفحة التالية، التحديث وإعادة المحاولة.
- [ ] احفظ العناصر والعدادات الأربعة و`totalCount` وبيانات الصفحة والبحث والفلتر وحالات التحميل وFailure داخل الـState.
- [ ] ميز بين فشل التحميل الأولي وفشل التحديث وفشل تحميل صفحة إضافية؛ إعادة المحاولة تستهدف العملية نفسها.
- [ ] نفذ البحث والفلترة عبر API، مع debounce مقترح 350ms.
- [ ] عند تغيير البحث أو الفلتر، ابدأ من الصفحة 1 ولا تخلط العناصر بالاستعلام القديم.
- [ ] استخدم رقم جيل للاستعلام أو آلية مماثلة لتجاهل الاستجابات القديمة، حتى إذا تعذر إلغاء الطلب الفعلي.
- [ ] امنع طلب الصفحة نفسها بالتوازي وتكرار العناصر عند الدمج بالمعرف.
- [ ] فشل الصفحة التالية يحتفظ بالعناصر الحالية ولا يقدم رقم الصفحة الناجحة.
- [ ] احسب إمكانية الاستمرار من بيانات الصفحة و`totalCount`، مع حماية من الصفحات الفارغة والحلقات المتكررة.
- [ ] لا تحسب العدادات العامة من الصفحة الحالية ولا من `totalCount`؛ استخدم قيم الخادم.
- [ ] ألغِ debounce والاشتراكات عند إغلاق ViewModel وتجنب emit بعد الإغلاق.

- [ ] الحد الإجمالي 3 صور شامل المحفوظ بالفعل، مع إزالة المفاتيح المكررة.
- [ ] لا ترسل readUrl أو مسار الملف المحلي بدل storageKey.
- [ ] إذا نجح الرفع وفشل الربط، احتفظ بالمفتاح لإعادة الربط دون إعادة الرفع بلا داعٍ.
- [ ] لا تضف حد حجم جديدًا غير موثق؛ الحد المحلي الحالي يحتاج مطابقته بعقد الرفع، ولا تعتبره ضمانًا من هذه الوثيقة.
- [ ] استخدم `evidenceUrls` في تفاصيل السائق كمصفوفة روابط. لا تخلطها برد تفاصيل مسؤول التوصيل الذي يستخدم `evidencePhotos` كمصفوفة كائنات يحتوي كل منها على `url`.
- [ ] روابط الصور الجديدة تحتوي `readToken` مشفرًا خاصًا بملف واحد وصالحًا لمدة 15 دقيقة. اعرض الرابط كاملًا مباشرة في `Image.network` دون Bearer، ولا تحذف أو تعِد تكوين معاملاته. `readToken` ليس JWT الجلسة.
- [ ] الحصول على تفاصيل البلاغ والروابط الجديدة ما زال يتطلب جلسة مصادقًا عليها عبر Interceptors الموجودة.
- [ ] إذا كان الرابط نسبيًا مثل `/api/v1/uploads/content?...` فحلّه مقابل أصل API المكوّن من scheme وhost وport، دون تكرار `/api/v1`، مع الحفاظ على query والتوقيع كما أعادهما الخادم.
- [ ] عند انتهاء صلاحية الرابط، أعد طلب تفاصيل البلاغ للحصول على روابط جديدة واستبدل القديمة في State. لا تحفظ الرابط كرابط دائم، ولا تعِد رفع الصورة أو ربطها بسبب انتهاء رابط القراءة.
- [ ] اجمع طلبات تجديد الروابط المتزامنة في طلب تفاصيل واحد، وحدد محاولة تجديد واحدة لكل دورة فشل حتى لا تنشئ حلقة لا نهائية. إذا استمر الفشل، اعرض خطأ الصورة مع إعادة محاولة واعية.
- [ ] رابط القراءة القديم `GET /api/v1/uploads/content?key=...` دون readToken يحتاج Bearer في طلب الصورة نفسه. فضّل إعادة قراءة التفاصيل للحصول على الرابط الموقع؛ إن احتاج التدفق دعم الرابط القديم، استخدم توكن الجلسة الحالي فقط مع خادم التطبيق الموثوق.
- [ ] لا تضف JWT إلى query ولا ترسل Bearer إلى مضيف CDN خارجي. لا تسجل الرابط الموقع أو readToken أو JWT في logs أو analytics أو رسائل الأخطاء؛ الرابط الموقع يمنح قراءة الملف طوال صلاحيته.
- [ ] احترم `Cache-Control: no-store` و`Referrer-Policy: no-referrer`، وراجع أي cache مخصص حتى لا يحفظ الروابط/الاستجابات الموقعة حفظًا دائمًا.
- [ ] رفع الملف وربطه عمليتان منفصلتان؛ لا تعتبر المعاينة المحلية أو نجاح الرفع دليلًا على الارتباط. بعد نجاح الربط أعد قراءة التفاصيل من الخادم.
- [ ] إذا كانت `evidenceUrls` فارغة، افحص body الربط وstorageKeys وissueId؛ إذا كانت ممتلئة والصورة لا تفتح، افحص طلب الصورة ورمز HTTP دون تسريب الرابط الموقع. 401 للرابط القديم يستدعي تحديث التفاصيل أو مصادقة طلب الصورة القديم.
- [ ] احصر خطأ تحميل الصورة في موضع الصورة، دون إسقاط شاشة التفاصيل كلها.

## 10. مراجعة إنشاء البلاغ الموجود

المسار:

```http
POST /api/v1/driver/orders/{boxId}/report-issue
```

- [ ] تأكد أن boxId هو GUID الخاص بـTripStop، وليس رقم الطلب المعروض.
- [ ] طابق issueType مع القيم العشر في عقد الباك.
- [ ] الوصف اختياري، وبعد trim لا يتجاوز 250 حرفًا؛ لا تغير نصه الداخلي عند العرض.
- [ ] الشدة Low أو Medium أو High، والافتراضي Medium.
- [ ] حد الصور 3، والنجاح يعيد معرف البلاغ كسلسلة JSON.
- [ ] امنع الضغط المتكرر أثناء الإرسال.
- [ ] راجع أي retry interceptor؛ لا تسمح بإعادة POST الإنشاء تلقائيًا بعد timeout أو انقطاع ملتبس.
- [ ] بعد timeout أعد قراءة القائمة قبل السماح بإعادة إرسال واعية، ولا تدعِ أن مطابقة العنوان أو التوقيت تثبت نجاح الطلب السابق.

**اعتماد يحتاج حسمًا عند التنفيذ:** زر الإبلاغ في قائمة الدعم يفتح شاشة الإبلاغ دون سياق ظاهر في الاستدعاء الحالي، بينما إنشاء البلاغ يتطلب TripStop. افحص التدفق كاملًا: استخدم سياق طلب صالح أو اختيار طلب مدعومًا بالفعل. إذا لم يوجد تدفق صالح، سجّل الحاجة لقرار منتج/باك حول البلاغ العام؛ لا تختلق boxId أو endpoint أو اختيارًا وهميًا.

## 11. نظام الأخطاء الإلزامي

استخدم `Failure` في State، و`ApiExceptionMapper` و`ApiResult` الحاليين. لا تنشئ نظام أخطاء موازيًا.

التوقيع الصحيح الموجود في الكود يستخدم معامل failure مسمى:

```dart
ApiErrorWidget.fromTypedFailure(
  failure: failure,
  onRetry: () => viewModel.doIntent(retryEvent),
)
```

| الحالة | العرض المطلوب |
|---|---|
| تحميل أولي | Loader/Shimmer الموجود |
| فشل دون بيانات قابلة للعرض | ApiErrorWidget |
| فشل تحديث أو صفحة إضافية مع بيانات | إبقاء المحتوى وInlineApiErrorWidget |
| نجاح بنتيجة فارغة | EmptyStateWidget أو مكوّن الفراغ الحالي وفق قواعد المشروع |
| فشل إرسال نموذج أو إضافة صور | إبقاء النموذج وعرض خطأ العملية في موضعها |

- [ ] لا تختزل Failure إلى String وتفقد النوع والكود.
- [ ] لا تكرر switch لأخطاء الشبكة داخل الشاشات.
- [ ] اتخذ قرارات الدومين باستخدام `failure.exception.backendErrorCode`، لا نص رسالة مترجمة.
- [ ] أعد استخدام نظام الترجمة الموجود لأي نص جديد.
- [ ] لا تضف Snackbar أو Toast أو feedback pattern جديدًا لمجرد أخطاء API.
- [ ] لا تمرر callback لشات غير موجود إلى مكونات الأخطاء.
- [ ] تعامل مع 401/403 من خلال آلية المصادقة والصلاحيات الحالية، دون اختراع تسجيل خروج لكل خطأ.

| كود الباك | السلوك |
|---|---|
| DRIVER_SUPPORT_ISSUE_NOT_FOUND | عرض غير متاح دون FakeData |
| DRIVER_SUPPORT_PHOTOS_INVALID | تصحيح المفاتيح قبل إعادة الربط |
| DRIVER_SUPPORT_PHOTO_UPLOAD_INVALID | رفع صورة صحيحة من المستخدم الحالي |
| DRIVER_SUPPORT_PHOTO_MISSING | إعادة الرفع واستخدام المفتاح الجديد |
| DRIVER_SUPPORT_PHOTO_LIMIT | تحديث التفاصيل وإظهار حد الصور |
| DRIVER_SUPPORT_ISSUE_TERMINAL | تحديث التفاصيل وإيقاف إضافة الصور |
| DRIVER_SUPPORT_ISSUE_INCOMPLETE | إعادة قراءة التفاصيل دون تكرار تعديل تلقائي |

إعادة المحاولة تعيد العملية الفاشلة فقط، مع استثناء إعادة إنشاء البلاغ بعد timeout كما سبق.

## 13. خطة الاختبارات والتحقق

اكتب اختبارات سلوكية مركزة تحت `test/features/driver/driver_support_tickets/`، ووسّع اختبارات `delivery_issues` الحالية عند تعديل سلوكها.

- [ ] Mapper: قائمة وتفاصيل وحقول ناقصة وnull وحالات غير معروفة، دون اختلاق طلبات أو تواريخ.
- [ ] القائمة: العدادات مستقلة عن البحث والصفحات، query صحيح، وتجاهل نتيجة بحث قديمة.
- [ ] الصفحات: فشل الصفحة التالية يحتفظ بالعناصر ويعيد الصفحة الصحيحة دون تكرار.
- [ ] التفاصيل: تحميل بالمعرف، غياب المعرف، عدم توفر البلاغ، عدم عرض FakeData أو زر شات.
- [ ] الأخطاء: ApiErrorWidget عند الفشل الكلي وInlineApiErrorWidget مع محتوى صالح، والفراغ ليس فشلًا.
- [ ] الصور: حد الثلاث، deduplication، إرسال storageKey، إعادة الربط بعد فشل دون إعادة رفع، والتعامل مع بلاغ انتهى أثناء الإضافة.
- [ ] الإنشاء: لا إعادة POST تلقائية عند timeout، وتحديث القائمة قبل أي إعادة إرسال.
- [ ] realtime: الحدث الصحيح وإعادة الاتصال يحدثان البيانات وإلغاء الاشتراك يمنع listeners المتراكمة.
- [ ] تحميل الصور: عرض الرابط الموقع دون Bearer والحفاظ على readToken، وحل الرابط النسبي دون تكرار `/api/v1`.
- [ ] انتهاء الرابط: تحديث التفاصيل واستبدال الروابط دون إعادة رفع/ربط، ودمج محاولات التجديد المتزامنة ومنع حلقات إعادة المحاولة.
- [ ] الروابط القديمة: المصادقة عند الحاجة مع خادم التطبيق فقط، وعدم إرسال JWT لمضيف خارجي أو إضافته إلى query، وعدم تسجيل الروابط الموقعة أو readToken.
- [ ] تشخيص الصور: فرّق بين مصفوفة فارغة بسبب الربط وبين رابط موجود يفشل تحميله، ولا تخلط evidenceUrls الخاصة بالسائق بـevidencePhotos الخاصة بالموظف.

نفذ الأوامر المناسبة من جذر المشروع بعد التنفيذ:

```bash
dart run build_runner build --delete-conflicting-outputs
flutter analyze
flutter test
```

- [ ] نسق الملفات المعدلة فقط وراجع diff الملفات المولدة، دون تغييرات غير مرتبطة.
- [ ] تحقق يدويًا بعد نشر الباك: قائمة، بحث، فلتر، صفحات، تفاصيل، رفع وربط صور، تغير الحالة من الموظف، reconnect، انقطاع شبكة وبلاغ منتهٍ.
- [ ] إذا لم ينشر الباك، اذكر أن التحقق الحقيقي من API معلق؛ نجاح اختبارات Flutter لا يثبت أن المسارات منشورة.

## 14. شروط القبول والتسليم

- [ ] القائمة والتفاصيل تستخدمان بيانات API في تدفق الاستخدام الحقيقي.
